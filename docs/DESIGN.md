# Walky — офлайн-«облако» на флешке

Проект: демон + GUI для двусторонней синхронизации локальной папки с хранилищем на
USB-флешке, которая играет роль «сервера» Dropbox/Яндекс.Диска. Интернет не нужен,
транспорт — физическая флешка со специальной меткой.

Документ фиксирует решения, подводные камни и план работ. Версия 0.1 (обсуждение).

---

## 1. Что строим и чем это не является

Строим:

- **демон** (`walky daemon`), работающий в user-сессии systemd, который замечает
  подключение флешки, монтирует её (через udisks2), синхронизирует папку и
  отслеживает изменения через inotify + периодический скан;
- **хранилище на флешке**: контентно-адресуемые объекты + снапшоты (история версий),
  устойчивое к выдёргиванию, с возможностью восстановления на чистой машине;
- **CLI** (`walky init|attach|status|sync|verify|gc|restore|export`);
- **GUI** на GTK4/libadwaita: статус, прогресс, последние 5 файлов, извлечение.

Не является:

- не бэкап-система (флешка — единственная копия, пока не сделана вторая);
- не сетевая синхронизация (Syncthing/rsync over ssh) — это «sneakernet»;
- не ФС с прозрачным доступом (см. опцию `current/` в §4.2, но по умолчанию
  содержимое флешки — непрозрачное CAS-хранилище).

Ключевая особенность: **источник истины по истории — флешка**, а не локальный диск.
Локальный диск может быть потерян; новая машина должна восстановиться с флешки.

## 2. Ключевые решения (TL;DR)

| Вопрос | Решение | Почему |
|---|---|---|
| Модель синхронизации | двусторонняя, 3-way merge относительно последнего общего снапшота (base) | как Dropbox; без base невозможно отличить «удалено» от «ещё не скачано» |
| Хранилище | CAS: blake3-хеш → объект; мелкие файлы упакованы в паки; снапшоты = манифесты | дедуп между версиями, переименования бесплатны, устойчивость к сбоям |
| ФС флешки | **ext4 (+LUKS2)**, если только Linux; exFAT — если нужен Windows/macOS | hardlink/symlink/права/журнал vs кросс-платформенность |
| Обнаружение | user-демон + D-Bus udisks2 (без root); опционально udev+systemd для headless | udev не умеет стартовать user-юниты; udisks уже монтирует в GNOME |
| Язык ядра | **Go** (один статический бинарник, godbus, modernc/sqlite, blake3, zstd) | вы уже в Go; UI тонкий |
| Язык UI | **Vala + GTK4/libadwaita** (отдельный процесс, D-Bus) | минимум кода для нативного GNOME; падение UI не ломает синк |
| Альтернатива | всё на Rust (gtk4-rs + zbus) | если хочется один язык и не смущает borrow checker |
| Интеграция в GNOME | окно + портал Background + GNotification; опционально SNI-трей | на машине уже стоит `appindicatorsupport`, но портал — «родной» путь |
| Единица истории | поколение (generation) + манифест, HEAD пишется последним | атомарность коммита без журнала ФС |

### 2.1 Утверждено (2026-11-24)

1. Флешку читает **только Linux** → **ext4 + LUKS2**, без exFAT-компромиссов.
2. Машин **несколько** → полная модель: `machine-id`, per-machine base,
   поколения, предупреждение об устаревшем base.
3. Конфликты — **сохранять оба** варианта (`name.conflict-<host>-<time>.ext`).
4. Стек — **Go-ядро/CLI + Vala + GTK4/libadwaita UI** по D-Bus.
5. Целевая ФС и шифрование означают: симлинки, права, xattr и hardlinks
   поддерживаются нативно; метаданные всё равно дублируются в манифест
   (для восстановления на другую машину и для `export`).

Следствия для реализации: `require_luks = true` по умолчанию, `current/`-ферма
становится возможной (hardlink на ext4), Windows-совместимость не нужна —
можно свободно использовать `renameat2`, `O_NOFOLLOW`, `fsync` каталогов.

## 3. Подводные камни, которые нужно учесть

### 3.1 Данные и файловая система

1. **Флешка — не бэкап.** Она теряется, ломается, изнашивается. Нужны: вторая флешка
   (ротация), `walky verify` после записи, предупреждение в UI, если реплика одна.
   Правило 3-2-1 никто не отменял, «офлайн Dropbox» его не заменяет.
2. **ext4 vs exFAT.** exFAT: нет прав, симлинков, hardlink, xattr; регистронезависима;
   mtime с точностью 10 мс; кластер 32–128 КБ; нет журнала. ext4: всё есть, но
   Windows не прочитает. LUKS + ext4 — лучший вариант для «только Linux».
   Метаданные (mode/uid/symlink/xattr) в любом случае писать в манифест, чтобы
   восстановление было точным.
3. **Кластерный оверхед и мелкие файлы.** 200 тыс. файлов по 20 КБ на exFAT с
   кластером 128 КБ — это ~25 ГБ мусора. Решение: упаковка мелких объектов в паки
   по 16–32 МБ. Заодно уходит `fsync` на каждый файл.
4. **Нет журнала на exFAT.** Выдёргивание во время записи → «грязная» ФС, fsck.
   Нужны: `-o noatime,flush`, запись только через tmp+rename, кнопка «Извлечь»
   (`udisksctl unmount` + `power-off`), проверка `fsck` при грязном флаге.
5. **Атомарность.** Инвариант: HEAD на флешке всегда указывает на полностью
   записанный манифест, все блобы которого уже на месте и проверены. Порядок:
   объекты/паки → fsync → манифест(tmp→rename) → meta → `machines/<id>.json` →
   HEAD(tmp→rename) → fsync каталогов. Сбой до HEAD = безобидный мусор для GC.
6. **Прерывание синка.** Выдернули флешку / уснул ноутбук / ENOSPC. Демон обязан:
   прервать, пометить устройство грязным, **не** обновлять локальный base, при
   повторном подключении докатить с начала коммита. Локальные временные файлы
   удаляются при старте (журнал намерений).
7. **Сон/гибернация.** Подписка на `org.freedesktop.login1` `PrepareForSleep`:
   остановить запись и `fsync` до засыпания. Иначе USB отвалится посреди пака.
8. **Автосуспенд USB.** Дешёвые флешки отваливаются при `usbcore.autosuspend`:
   udev-правило `ATTR{power/control}="on"` для этой модели + `queue/scheduler=none`.
9. **Регистр и Unicode.** exFAT регистронезависима → `README` и `readme` схлопнутся.
   macOS отдаёт NFD, Linux NFC → на exFAT коллизии. Сравнивать пути в NFC,
   при применении на регистронезависимую ФС — явная ошибка, не «тихая» перезапись.
10. **Спецфайлы.** Симлинки (на exFAT материализовать нельзя), hardlinks (дублировать,
    но дедуп в CAS делает это бесплатным на флешке), sparse-файлы (хранить карту
    дыр), FIFO/сокеты/устройства — пропускать с логом.
11. **Git-репозитории.** `.git` меняется постоянно: packfiles переписываются при
    `git gc`, появляются `*.lock`. Синк «на лету» может поймать состояние, где ref
    ссылается на ещё не записанный объект. Практика: если в дереве есть `*.lock` —
    отложить синк на 30 с; не синхронизировать `.git/index.lock`; помнить, что
    снапшот атомарен по файлам, а не по репозиторию (откат всегда возможен).
12. **Мусор в проектах.** `node_modules`, `target/`, `build/`, `.venv`, `__pycache__`,
    `.cache`, `*.iso` — 15 ГБ превращаются в 150 ГБ. Дефолтный список исключений
    + `.walkyignore` в стиле gitignore.
13. **mtime — недоверенный.** Точность 2 с/10 мс, часовые пояса, разные машины.
    Сравнивать только (размер, хеш); mtime использовать как эвристику кэша.

### 3.2 Синхронизация

14. **Три состояния, а не два.** Нужен base — манифест последнего успешного синка
    этой машины. Иначе нельзя отличить удаление от «файл появился на другой машине».
15. **Tombstones.** Удаление должно быть явным событием с поколением, иначе старая
    машина воскресит файл. Хранить N дней; GC только когда все машины ушли дальше.
16. **Конфликты.** Обе стороны изменили → не перезаписывать. Политика по умолчанию:
    сохранить оба (`name.conflict-<host>-<timestamp>.ext`), оригинал — по политике
    «кто новее» или «локальный». Удаление против изменения → побеждает изменение
    (данные важнее).
17. **Несколько машин.** Флешка — транспорт и общая история. У каждой машины свой
    base (`machines/<id>.json` на флешке + локально). Поколения образуют цепочку,
    HEAD двигается при каждом коммите. Машина, не синхронизировавшаяся дольше
    retention, при подключении получает предупреждение и требует явного решения.
18. **Свободное место.** Preflight: оценить объём новых объектов + манифест + 10 %.
    Не начинать, если не хватает; понятная ошибка в UI. При ENOSPC — корректный
    abort, HEAD не двигать.
19. **GC.** Mark-and-sweep от всех удерживаемых манифестов и всех `machines/*.json`.
    Не удалять блобы, на которые ссылается другая машина. Запускать по расписанию
    или при нехватке места, не во время синка.
20. **Переименования.** Дедуп по хешу делает их бесплатными по трафику; для истории
    можно детектить по inode-кэшу, но в MVP не обязательно.
21. **Один писатель.** `flock` на `/WALKY/lock` + pid/hostname/boot_id. Второй
    экземпляр (или вторая машина, если флешку вставили в обе) — отказ с сообщением.

### 3.3 Безопасность и целостность

22. **blake3 на каждый объект**, проверка при записи и при чтении. `walky verify`
    (полный) и быстрый `--quick` (HEAD + последний коммит) после подключения.
23. **Подмена флешки.** Маркер-файл может быть подделан: в конфиге — allowlist
    `repo_id`, проверка `fs_uuid`; опционально подпись манифеста (ed25519).
24. **Path traversal при restore.** Только относительные пути, без `..`, без
    абсолютных, без следования симлинкам. В Go — `os.Root` (1.24+) или
    `openat2(RESOLVE_BENEATH)`; в Rust — `cap-std`.
25. **Шифрование.** LUKS2 на всю флешку (просто и прозрачно) с keyfile в
    `~/.config/walky/` + fallback на пароль; либо app-level (age) ценой
    совместимости с Windows. Без шифрования потеря флешки = утечка кода.
26. **Права при восстановлении.** uid/gid могут не совпасть; режим «восстановить
    как текущий пользователь» по умолчанию, `--preserve-owner` — опция.
27. **Логи на флешке** ротировать (5 файлов по 1 МБ), иначе лог съест место.

### 3.4 Эксплуатация

28. **inotify.** Лимит `max_user_watches` (часто 8192) — на 20 тыс. каталогов нужно
    524288. Overflow (`IN_Q_OVERFLOW`) → полный перескан. Watch на каталог, не на файл.
29. **Стоимость скана.** 200 тыс. файлов: тёплый скан по stat-кэшу ~1–3 с, холодный
    хеш 15 ГБ ~10–30 с (blake3, NVMe). Параллелить осторожно: на HDD 2–4 воркера,
    на NVMe — больше.
30. **Скорость USB.** USB 2.0: 15–25 МБ/с → первичные 15 ГБ ≈ 10–17 мин.
    USB 3.0: 50–150 МБ/с → 2–5 мин. Инкремент — секунды. То есть «не медленнее
    интернета» — да для инкремента, и примерно так же для первой заливки на USB 3.
    Узкое место — не пропускная способность, а `fsync` и мелкие файлы → паки.
31. **Износ флешки.** Дешёвые TLC/QLC умирают от перезаписи; паки пишутся
    append-only, старые не перезаписываются, но каждая версия — новые паки.
    Для 15 ГБ и ежедневных инкрементов 128 ГБ хватит надолго; 32 ГБ — впритык.
32. **Размер флешки.** 15 ГБ данных + история (дедуп обычно +20–40 %) → минимум
    64 ГБ, комфортно 128 ГБ.
33. **Совместимость формата.** `format: 1` в маркере, проверка версии, миграции.
    Старый демон не должен писать в новый формат.
34. **Один экземпляр и автозапуск.** D-Bus-активация user-юнита, `Type=dbus`,
    `Restart=on-failure`; GUI поднимает демон по требованию.

## 4. Архитектура

### 4.1 Компоненты

```
┌─────────────────────────────┐        D-Bus io.github.ijin.Walky1
│ walky daemon (Go)           │◄──────────────────────────────┐
│  device  ← udisks2 signals  │                               │
│  scan    → SQLite index     │        ┌──────────────────────┴─────┐
│  store   → CAS/packs        │        │ walky-ui (Vala, GTK4/Adw)  │
│  sync    → 3-way merge      │        │  статус, прогресс, last 5  │
│  api     → D-Bus server     │        │  настройки, eject          │
└──────────┬──────────────────┘        └────────────────────────────┘
           │ mount /run/media/$USER/WALKY
           ▼
      USB flash (ext4+LUKS)
```

CLI `walky` — тот же бинарник, что демон (`walky daemon` / `walky status`), общается
с демоном по D-Bus, а при `--direct` работает с хранилищем напрямую (для восстановления
на живой системе и для тестов).

### 4.2 Формат хранилища на флешке

```
/WALKY/
  walky.json                  # маркер: format, repo_id, fs_uuid, label, created
  HEAD                        # {"gen":42,"manifest_sha256":"..."} — пишется последним
  objects/ab/cd/<blake3>      # объекты > 1 МиБ, по одному файлу
  packs/pack-<id>.pack        # мелкие объекты, ~16–32 МиБ, каждый объект сжат отдельным кадром
  packs/pack-<id>.idx         # отсортированный (hash,offset,len), для поиска
  snapshots/00000042.jsonl.zst# полный манифест поколения
  snapshots/00000042.meta.json# machine, parent, time, stats, подпись (опц.)
  machines/<machine-id>.json  # base_gen этой машины, hostname, last_sync
  trash/<gen>/...             # удалённые пути, N дней
  log/walky-YYYYMMDD.log
  lock                        # flock
```

Манифест — JSONL, отсортированный по пути, zstd:

```json
{"p":"docs","t":"d","m":493}
{"p":"src/main.go","t":"f","s":1234,"m":420,"h":"b3:9f2c…","mt":1732456789123456789}
{"p":"link","t":"l","target":"../x"}
{"p":"old.txt","t":"x","gen":41}
```

`t`: `f` файл, `d` каталог, `l` симлинк, `x` tombstone.
Для больших файлов — `b`: список чанков (FastCDC, средний 1–4 МиБ) для дедупа
между версиями образов/архивов; для остальных `h` — хеш целого файла.

Полный манифест на 200 тыс. файлов ≈ 20–25 МБ JSON → 5–8 МБ zstd. При retention
~40 поколений это 200–300 МБ — приемлемо; при желании позже перейти на дельты
от родителя (полный каждые 10 поколений).

**Опция «человекочитаемый» `current/`** (только ext4): hardlink-ферма на последний
снапшот, чтобы флешку можно было читать без walky. Минус: правка файла на флешке
портит блоб (тот же inode) — лечится `chmod 0444` + `verify`/repair, но это
дополнительный риск. Поэтому: MVP — `walky export <gen> <dir>`, `current/` — позже
и опционально.

### 4.3 Локальное состояние

```
~/.config/walky/config.toml      # настройки
~/.local/state/walky/
  index.db                       # SQLite: путь, dev, ino, size, mtime, ctime, hash
  base.jsonl.zst                 # base-манифест последнего успешного синка
  journal.jsonl                  # намерения на время коммита (восстановление)
~/.local/share/walky/trash/      # локальная корзина при удалении «с флешки»
~/.cache/walky/locations.db      # hash → (pack, offset), rebuildable
```

Конфиг (TOML):

```toml
[repo]
path = "~/Sync"
repo_id = "…"            # allowlist, защита от чужой флешки с таким же маркером

[sync]
mode = "two-way"         # two-way | push-only
conflict = "copy"        # copy | newest | local-wins
debounce_ms = 3000
full_scan_min = 10

[exclude]
patterns = ["**/node_modules", "**/target", "**/.venv", "**/__pycache__",
            "**/.cache", "**/*.lock", "**/*.tmp"]
max_file_size = "8G"

[retention]
daily = 14
weekly = 8
monthly = 6
trash_days = 30

[device]
require_luks = true
auto_sync = true
eject_after_sync = false
```

### 4.4 Алгоритм синхронизации

Вход: `L` — локальный манифест (после скана), `S` — манифест HEAD на флешке,
`B` — base этой машины. Для каждого пути:

| L vs B | S vs B | Действие |
|---|---|---|
| = | = | ничего |
| изменён | = | **push** |
| = | изменён | **pull** |
| изменён | изменён, L == S | сходятся, обновить base |
| изменён | изменён, L != S | **конфликт** |
| удалён | = | push tombstone (в корзину на флешке) |
| = | удалён | удалить локально (в локальную корзину) |
| удалён | изменён | конфликт: воскресить изменённую версию |

Порядок фаз:

1. Перескан локальной папки (inotify-события + полный скан по таймеру).
2. Проверка флешки: маркер, `repo_id`, версия формата, `fsck`-флаг, свободное место.
3. Расчёт плана (push/pull/conflict) и объёма.
4. **Pull-фаза**: скачать недостающие объекты, применить атомарно
   (tmp в том же каталоге → fsync → `renameat2(RENAME_NOREPLACE)` → fsync каталога),
   восстановить mode/mtime/symlink.
5. **Push-фаза**: записать новые объекты/паки (tmp → fsync → rename), затем коммит
   манифеста по протоколу §4.2, обновить `machines/<id>.json`, затем HEAD.
6. Обновить локальный `base` **только после** успешного HEAD и применённых pull.
7. События в UI (сигналы), запись в журнал, опционально eject.

Почему pull раньше push: если push упадёт, локальный base не сдвинут, а скачанное
уже применено — это безопасное состояние (при следующем запуске просто пересчитается).

### 4.5 Инварианты надёжности

- **I1.** HEAD всегда консистентен: манифест на месте, sha256 совпадает, все
  упомянутые объекты существуют.
- **I2.** base не двигается, пока коммит на флешке не завершён.
- **I3.** Ни один локальный файл не удаляется без копии в корзине (локальной или
  на флешке).
- **I4.** Прерывание в любой момент → следующий запуск либо откатывает мусор, либо
  докатывает; «половинчатого» HEAD не бывает.
- **I5.** Чтение всегда идёт от HEAD; лишние объекты игнорируются и собираются GC.

Тестировать I1–I4 инъекцией сбоев: `SIGKILL` в каждой точке протокола (failpoints),
`dmsetup` target `flakey`/`error` на loop-устройстве, выдёргивание loop-устройства.

### 4.6 Конфликты

- По умолчанию: оба варианта сохраняются, локальный переименовывается в
  `<name>.conflict-<host>-<YYYYMMDD-HHMMSS>.<ext>`; в UI — запись «конфликт».
- Опции: `newest` (по mtime, с оговоркой о недоверенных часах), `local-wins`.
- Удаление vs изменение → изменение побеждает, в лог и UI.
- Конфликты не блокируют остальную синхронизацию.

### 4.7 Retention и GC

- Политика: 14 daily + 8 weekly + 6 monthly (настраивается), корзина 30 дней.
- Mark: все манифесты политики + `machines/*.json` (base других машин) + trash.
- Sweep: удалить неотмеченные объекты/паки; пересобрать `locations.db`.
- Запуск: по расписанию, при нехватке места, вручную `walky gc`; никогда — во время
  синка и никогда при `dirty`-флаге.

## 5. Обнаружение флешки и systemd

### 5.1 Рекомендуемый вариант: user-демон + udisks2

- Демон подписывается на `org.freedesktop.UDisks2` (`InterfacesAdded`,
  `PropertiesChanged`, `Device.Removed`), фильтрует блочные устройства с
  `IdLabel`/`IdUUID` из конфига, читает `/WALKY/walky.json` после монтирования.
- Монтирование — udisks (GNOME и так это делает); опции `noatime`; при
  необходимости демон сам зовёт `Filesystem.Mount`.
- Плюсы: без root, работает в сессии, можно показать UI, корректно размонтировать.
- Минус: не работает без логина (для headless — §5.2).

`~/.config/systemd/user/walky.service`:

```ini
[Unit]
Description=Walky offline drive sync
Documentation=man:walky(1)
PartOf=graphical-session.target
After=graphical-session.target
StartLimitIntervalSec=0

[Service]
Type=dbus
BusName=io.github.ijin.Walky1
ExecStart=/usr/bin/walky daemon
Restart=on-failure
RestartSec=3
Slice=background.slice
NoNewPrivileges=yes
PrivateTmp=yes
ProtectControlGroups=yes
ProtectKernelModules=yes

[Install]
WantedBy=graphical-session.target
```

`Type=dbus` + `BusName` даёт активацию по требованию: GUI/CLI просто вызывают метод,
systemd поднимает демон.

### 5.2 Headless / без логина

udev не может стартовать user-юниты, поэтому для системного режима:

```udev
ACTION=="add", SUBSYSTEM=="block", ENV{ID_FS_LABEL}=="WALKY", \
  TAG+="systemd", ENV{SYSTEMD_WANTS}+="walky@%k.service"
```

`walky@.service` — системный шаблон с `User=` и `ExecStart=/usr/bin/walky daemon
--device /dev/%i`. Маркер всё равно проверять в самом демоне (label подделывается).

### 5.3 Жизненный цикл

- Старт: просканировать уже смонтированные устройства (флешку могли вставить до
  логина/запуска демона).
- Подключение: дождаться стабилизации монтирования (retry чтения маркера 5×200 мс),
  `walky verify --quick`, автосинк (если включён).
- Отключение: прервать текущий коммит, не двигать base, пометить «отключено
  небезопасно».
- Извлечение по кнопке: дождаться завершения коммита → `Filesystem.Unmount` →
  `Drive.PowerOff` → уведомление «можно вынимать».
- Сон: `PrepareForSleep` → пауза + fsync.

Плюс `.desktop` с `X-GNOME-UsesNotifications=true`, `DBusActivatable=true`,
иконка, `Keywords`.

### 6.3 D-Bus-контракт

```xml
<node>
  <interface name="io.github.ijin.Walky1">
    <method name="SyncNow"><arg type="b" direction="in" name="wait"/></method>
    <method name="Pause"><arg type="b" direction="in" name="paused"/></method>
    <method name="GetStatus"><arg type="a{sv}" direction="out" name="status"/></method>
    <method name="GetEvents"><arg type="u" direction="in" name="limit"/>
      <arg type="a(ssstt)" direction="out" name="events"/></method>
    <method name="Eject"/>
    <method name="Verify"><arg type="b" direction="in" name="full"/></method>
    <signal name="StateChanged"><arg type="s" name="state"/></signal>
    <signal name="Progress"><arg type="u" name="done"/><arg type="u" name="total"/>
      <arg type="t" name="bytes"/></signal>
    <signal name="FileDone"><arg type="s" name="path"/><arg type="s" name="op"/>
      <arg type="s" name="result"/></signal>
  </interface>
</node>
```

`GetStatus` возвращает `state`, `device`, `last_sync`, `pending`, `conflicts`,
`free_bytes`, `version`. Сигналы троттлить (≤10/с). UI не блокируется: все вызовы
асинхронные, прогресс — сигналами.

## 7. Выбор языка

| | Go | Rust | Vala |
|---|---|---|---|
| Ядро синка | ★★★★★ (горутины, статический бинарник, `godbus`, `modernc/sqlite`, `blake3`, `klauspost/zstd`) | ★★★★★ (`zbus`, `rusqlite`, `notify`, `serde`) | ★★ (мало библиотек, GC-рантайм для I/O не проблема, но экосистема бедная) |
| GTK4/Adw | ★★ (`gotk4`: cgo, лайфтаймы GObject, упаковка) | ★★★★ (`gtk4-rs`, `libadwaita`) | ★★★★★ (родной, минимум кода) |
| Скорость разработки | ★★★★★ | ★★★ | ★★★★ |
| Надёжность/тесты | ★★★★ | ★★★★★ | ★★★ |
| Один язык на всё | ★★★ (UI слабое место) | ★★★★★ | ★★★★ (ядро слабое) |
| Бинарник/зависимости | один статический | один статический | glib/gtk в системе |

**Рекомендация:** ядро и CLI — Go; UI — Vala (GTK4/libadwaita) отдельным процессом,
связь по D-Bus. Это даёт быстрый старт (вы уже в Go), нативный GNOME-вид и
развязку «UI упал — синк живёт». Если хочется один язык и есть время — всё на Rust
(`gtk4-rs` + `zbus` + `notify` + `rusqlite`), это самый «правильный» монолит.
Vala-монолит не советую: движок синка на Vala будет болью (хеши, zstd, SQLite,
тесты, конкурентность).

Структура репозитория:

```
core/                 # Go-модуль "walky", собирается независимо
  cmd/walky/          # main, CLI, daemon
  internal/store/     # CAS, паки, манифесты, коммит, GC
  internal/scan/      # обход, stat-кэш, хеширование, exclude
  internal/sync/      # 3-way merge, apply, конфликты
  internal/device/    # udisks2, монтирование, извлечение
  internal/index/     # SQLite
  internal/api/       # D-Bus-сервер + SNI
  internal/config/    # конфиг, валидация
ui/                   # Vala + GTK4/libadwaita, отдельный процесс, D-Bus
  src/                # Application.vala, Window.vala
  Makefile            # valac, без meson
data/                 # systemd units, .desktop, иконки, udev, sysctl
docs/
```

Границы: `core/` не знает про GTK, `ui/` не знает про формат хранилища — только
D-Bus-контракт `internal/api/walky1.xml`. Это позволяет тестировать движок без
дисплея и менять UI, не трогая синхронизацию.

## 9. Тестирование и метрики

- **Юнит/интеграция:** loop-образ ext4 + `udisksctl loop-setup`; два «клиента» с
  разными `machine-id` и общим loop-хранилищем.
- **Инъекция сбоев:** failpoints в протоколе коммита + `SIGKILL`; `dmsetup` targets
  `error` и `flakey`; отключение loop во время записи.
- **Property-тест:** случайные операции (create/write/delete/rename/mkdir/symlink)
  на двух сторонах, проверка инвариантов и сходимости после N раундов.
- **Fuzz:** парсер `walky.json`, `.meta.json`, манифеста, pack-idx.
- **Метрики:** первичный синк 15 ГБ (USB2/USB3), инкремент 100 файлов, тёплый скан
  200 тыс. файлов, RSS демона, CPU в простое < 1 %, отсутствие потерь данных.
- **Сценарии:** выдернули во время push; во время pull; места нет; чужая флешка с
  тем же label; два экземпляра; сон посреди коммита; флешка только для чтения.

## 10. Почему не взять готовое

| Инструмент | Что умеет | Почему не подходит |
|---|---|---|
| Syncthing | P2P-синк, версии, конфликты | нужна сеть и постоянно включённые узлы; нет транспорта «флешка» |
| Unison | двусторонний синк с архивом | нет истории/дедупа, нет UI, хрупок на больших деревьях |
| `rsync --link-dest` | снапшоты на ext4 | односторонне, нет merge/конфликтов, hardlink только ext4 |
| restic / borg | дедуп, шифрование, версии | это бэкап, а не двусторонний синк; нет base/merge |
| git-annex | буквально sneakernet, дедуп | симлинки/annex-UX, нужен git, медленно на 200 тыс. файлов |
| Dropbox/Яндекс | всё | интернета нет |

Вывод: логика «3-way merge + CAS + транспорт-флешка» уникальна, но идеи и формат
(паки, FastCDC, манифесты, GC) стоит заимствовать у restic/borg, а модель конфликтов —
у Syncthing/Unison.

## 11. Открытые вопросы

Решено: ФС (ext4+LUKS2), несколько машин, конфликты «сохранять оба»,
стек Go+Vala. Осталось уточнить до M4–M5:

1. **Глубина истории.** 14 daily + 8 weekly + 6 monthly — или «последние 30
   версий», чтобы экономить место? От этого зависит размер флешки (64 vs 128 ГБ).
2. **Автосинк при подключении или по кнопке?** Сейчас в конфиге `auto_sync = true`
   и уведомление; eject — вручную.
3. **Нужен ли «прозрачный» `current/` на флешке?** Теперь возможен (ext4, hardlink),
   но правка файла на флешке портит блоб — нужен `chmod 0444` и repair при verify.
4. **Одна флешка или две (ротация)?** Для реальной сохранности — две; вторая
   реплика не обязана быть постоянно подключена.
5. **LUKS: keyfile + пароль или только пароль?** Keyfile удобнее (авто-unlock),
   но лежит на той же машине; TPM (`systemd-cryptenroll`) — компромисс.
